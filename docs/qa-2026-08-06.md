## A. Fixed this session

### A1 ✅ Phone number stored in three places (normalization)
**You asked twice, and you were right — it was a real normalization failure.**

The same fact lived in `users.phone`, `helper_profiles.contact_number` and
`parent_profiles.contact_number`, with nothing keeping them in agreement. That
is why the duplicate-number bug kept reappearing somewhere new: signup checked
one copy, profile-save checked another, account uniqueness trusted a third.

**Now:** `users.phone` is the single source of truth.

| Layer | Change |
|---|---|
| Writes | `helper/update_profile.php` and `parent/update_profile.php` no longer write the profile columns. The number is saved once, by `carelink_claim_phone()`. |
| Reads | All 13 read sites now select `u.phone AS contact_number` — **same key, same API shape**, so no frontend change was needed. |
| Uniqueness | `phone_identity.php` went from three-column scan to one indexed lookup. |
| Data | `migration_2026_08_06_phone_normalization.sql` backfills `users.phone` from whichever copy had a value. |

**You must run** `backend/database/migration_2026_08_06_phone_normalization.sql`
(sections 1 and 2). Section 3 drops the dead columns — **deliberately left
commented out.** Run it in a few days once you're confident, not tonight.

### A2 ✅ Helper phone + email exposed in the browse directory
`parent/browse.php` returned every helper's phone number and email to any
employer paging the directory — no application, no message, no match. Neither
field was used by any screen. Both removed, plus the columns dropped from the
query. This was a live RA 10173 problem.

### A3 ✅ PayMongo: paid but nothing happened
Two separate causes.

1. **`payment_events` never existed on the live database** (it was only in a
   migration you had to paste in by hand). The webhook's first act is to write
   there; the prepare failed, the code read that as *"already processed"*,
   replied **200 OK**, and exited without granting anything. PayMongo saw
   success and never retried.
2. **My cooldown was wrong.** It fired on *cancel* too, so backing out of
   checkout locked you out for 3 minutes with a message implying you'd paid.

**Now:**
- All revenue tables auto-create (`shared/revenue_tables.php`) — no manual migration.
- The webhook throws instead of silently claiming success, so failures are visible and retried.
- **Payment no longer depends on the webhook at all.** `parent/confirm_subscription.php` asks PayMongo directly when you return from checkout. The webhook still covers "paid and never came back". Both share one guard, so a payment grants exactly one month either way.
- Tapping Upgrade again **resumes the same checkout session** instead of opening a second one.

### A4 ✅ Nothing shown after a successful purchase / popup vanished
The confirmation used `NotificationModal`, which **defaults to `autoClose` after
3.2 seconds** — that's the popup you saw disappear.

Replaced with `PlusWelcomeModal`: a celebration + receipt + mini-guide that
**never auto-dismisses**. Shows amount paid, start date, renewal date, boost
credits, and what each perk actually does.

Also added two pages to the parent guide ("Optional: CareLink Plus" and "What
Plus does NOT change").

### A5 ✅ Cover letter "3 previews" was unlimited
`ApplicationModal` ran `setGenCount(0)` on every open, so closing and reopening
handed out another three. The cap was cosmetic.

Now persisted per **helper + job** in AsyncStorage, so it survives reopening.
*Limitation:* client-side, so clearing app storage resets it. Cover letters
aren't a security boundary, so that's proportionate — but a server-side counter
is the correct long-term fix.

### A6 ✅ Login lockout evaporated on navigating away
`attemptsLeft` / `isLocked` were plain `useState` in a hook that unmounts with
the login screen. Press home, come back, lock gone.

Now persists the lock **expiry** (not a countdown), so it survives the app being
killed. Cleared on successful sign-in.
*Limitation:* still client-side. A real lockout belongs in `auth/login.php`
against the account — worth saying out loud in your defense rather than being
asked.

### A7 ✅ CareBot forgot the conversation on close — properly fixed this time
My previous fix was based on a wrong assumption. The real cause: **React Native's
`<Modal>` renders nothing when `visible={false}`**, so the whole chat panel
unmounts on close and takes its state with it. Nothing was resetting the
transcript — the component holding it stopped existing.

The transcript now lives in `CareBotContext`, which sits above the modal and
never unmounts. Cleared only on logout.

### A8 ✅ Video calls — Jitsi replaced with Daily.co
**The diagnosis matters:** the code used `https://meet.jit.si/<room>` — Jitsi's
*free public server*, which since 2023 requires the first participant to sign in
with Google/Facebook/GitHub and drops calls under load. Your testers hit a broken
free service, not broken code.

Rooms are now created server-side (`shared/create_call_room.php`) via Daily's
API, with a **2-hour expiry** so a link posted in chat can't be rejoined weeks
later. Still opens as a plain URL in the browser — which matters, because you
have no `eas.json`, so any native video SDK would need an EAS dev build first.

**You must add** `DAILY_API_KEY` to `backend/config.local.php`.

## B2. Second round (same day)

### B2-1 ✅ Verified without a Valid ID — the real hole
`canApproveUser` required *"every submitted document is Verified"*, which says
nothing about **which** documents were submitted. An applicant who uploaded only
a TESDA NC2 and a Police Clearance satisfied every check and became PESO
Verified with no ID and no Barangay Clearance on file.

**Now:** `carelink_missing_required_documents()` is the one authority on what's
required (`Valid ID`, `Barangay Clearance`), enforced **server-side** in
`verify_user.php` — the frontend guard alone was advisory, and anything that
grants verified status has to be checked where it's granted.

It is **not a hard block.** The officer gets exactly what you described:
*"This applicant has not submitted: Valid ID. Approving now marks them PESO
Verified without it. Confirm to proceed anyway."* Overrides are written to the
error log with the officer's id, so the decision has an owner.

### B2-2 ✅ Documents now say who verified them
New `DocumentStatusTag` — **"PESO Verified"**, "Awaiting PESO", "Rejected by
PESO" — plus a separate `AiScanTag` for the AI pre-check. The old pill just said
"Verified" next to an AI scan result, which read as though the app had cleared
the document. Verification is a PESO officer's decision and the UI now says so.

### B2-3 ✅ Can't take photos in messages
Chat offered gallery only. Added a camera button to both chat panels — the
wrong default for a hiring chat, where most things sent (a document, a room, an
ID) are photographed in the moment. Web falls back to the gallery, since
browsers have no camera capture.

### B2-4 ✅ PDFs uploaded fine but couldn't be viewed
Your clarification ("it works but cannot be seen") pointed at **serving**, not
uploading — and that was exactly it.

Documents are served through a signed URL:
```
serve_document.php?document_id=123&expires=…&token=…
```
That URL **never ends in `.pdf`**, no matter what the file is. But every viewer
checked `file_url.toLowerCase().endsWith('.pdf')` — which was therefore always
`false`. The app concluded the PDF was an image, rendered it as `<Image>`, and
you got a blank frame.

**The proof it was this:** the PESO document viewer checks `file_path` (the
stored path, which keeps its extension) and displayed PDFs correctly the whole
time. The helper and parent viewers checked `file_url` and didn't. Same data,
different field, opposite outcome.

**Why deployed-only:** locally, documents used to be served as a direct static
path that *did* end in `.pdf`, which masked the bug completely.

**Fixed:** new `lib/documentType.ts` — `isPdfDocument(filePath, fileUrl)` checks
the stored path first and treats the URL as a last resort. Applied to both
document-detail screens, both web profile screens, and `ImageZoomModal` (which
gained an explicit `isPdf` prop, since it only ever receives a URL).

The server was already correct — it detects the real MIME with `finfo` and sends
`Content-Type: application/pdf` with `Content-Disposition: inline`. Nothing
needed changing there.

Also fixed while in the area: `get_documents.php` returned neither
`file_path_back` nor `file_url_back`, so a freshly uploaded **back side** looked
missing until the next full profile load.

### B2-6 ✅ Guide said "complete your details", modal showed everything ticked
Not a display glitch — the two screens had **different definitions of the same
thing**, and each was internally consistent:

| | Setup guide | Edit Profile modal |
|---|---|---|
| "Personal" done when… | `contact_number` **and** `address` | first + last name only — *"contact number is optional"* |

Names come from signup and are always present, so the modal's Personal section
was green from the moment the account existed. An employer with a name and an
address but **no contact number** was told two contradictory things.

**Fixed:** one shared authority, `lib/parentProfileCompletion.ts`, read by both.
The guide's steps now map **one-for-one** onto the modal's sections (Contact ·
Address · Household · Documents), so a tick cannot mean different things in two
places again.

**Judgement call worth knowing:** contact number is no longer "optional" for
completion. PESO verifies a household partly by being able to *reach* it, and
the guide's own wording says "so helpers and PESO can reach you" — treating it
as optional is what let an unreachable profile look finished.

### B2-8 ✅ Direct hire — completed properly (supersedes B2-5)

**A design decision was reversed, and it matters.** The first pass delivered the
offer to the helper immediately, with acceptance gated until PESO approved.
That was wrong: if PESO rejects an offer for a sub-minimum salary or an unlawful
rest-day arrangement, **the helper has already read those terms**. Showing a
kasambahay unvetted terms is precisely the harm the review step exists to
prevent. It now follows the plan — delivery is held until approval.

The offer has three stages, enforced in `shared/direct_hire.php`:

| Stage | Job post | Invite | Who is told |
|---|---|---|---|
| Created | `Pending` | `peso_review` | **Employer only** |
| PESO approves | `Open` | `pending` | Helper receives the offer and can respond |
| PESO rejects | `Rejected` | `cancelled` | Employer only — the helper never learns it existed |

Delivery lives in one function so there is exactly one place that can put an
offer in front of a helper.

**Defence in depth:** `respond_invite.php` independently refuses an *accept*
unless the post is `Open`. Delivery already prevents this, so it should be
unreachable through the UI — but "the helper agreed to these terms" is the fact
a contract is built on, and if that can ever attach to unvetted terms the review
step is decorative. The guard costs nothing and survives a future change to the
delivery path.

**Frontend:** "Hire Directly" on the helper profile opens
`DirectHireOfferModal`, which collects the same terms a public post requires —
title, category, duties, salary (₱7,000/month floor enforced both sides),
arrangement, hours, start date. The copy states plainly *why* the terms are
required, so an employer expecting a one-tap shortcut understands why there
isn't one.

**Known limitation:** wired into **mobile browse only.** The desktop branch
renders `ParentBrowseWeb`, a self-contained component that doesn't share the
mobile modal stack, so the button isn't there yet.

### B2-5 ⚠️ Direct hire — first pass (superseded by B2-8 above)
This is the "started, not finished" item.

**Done:**
- `migration_2026_08_06_direct_hire.sql` — adds `job_posts.visibility` (`public` | `direct_hire`), defaulting every existing post to `public`.
- Discovery filtered: `browse_jobs.php` and `recommendations.php` exclude `direct_hire` posts, so a private offer can never surface in search. Only ~2 queries needed changing, because everywhere else already works from a specific `job_post_id` the helper legitimately received.
- `parent/create_direct_hire_offer.php` — creates a **real** job post (same fields, `status='Pending'` so **PESO still reviews it**, same contract, same signatures) and delivers it as an Accept/Decline invite through the existing `job_invites` flow.

**The design point worth defending:** a job post isn't paperwork for CareLink's
benefit — it's what forces the employer to state salary, arrangement and duties
*before* the helper commits. Remove it and the helper accepts blind, which is
what RA 10361 exists to prevent. So direct hire skips the **publicness**, not
the protections. It's faster, not lighter.

**Still to build:** the "Send Direct Hire Offer" button and form on the helper
profile screen. The backend is ready for it.
